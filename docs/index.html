What is Retrieval-Augmented Generation?

Connect an LLM to trusted, retrievable knowledge at answer time.

Retrieval-Augmented Generation (RAG) retrieves relevant evidence from an approved knowledge source and supplies it to a language model as context. The model then generates an answer grounded in that evidence rather than relying only on its trained parameters.

Core principle: A fluent answer is not necessarily a correct answer. RAG quality depends on extraction, metadata, access control, retrieval relevance, grounding and evaluation.

Typical request lifecycle

  1. Receive and validate the question; establish identity, tenant and permissions.
  2. Rewrite or decompose the query when useful.
  3. Retrieve candidate chunks using semantic and/or lexical search.
  4. Rerank candidates and remove duplicates.
  5. Assemble a bounded context with source references.
  6. Generate a grounded answer and validate citations.
  7. Return answer, sources and limitations; record safe telemetry.
02

Reference architecture

Separate the offline ingestion pipeline from the online question-answering path.

Ingestion pipeline

Documents→Parse / OCR→Normalize→Chunk + metadata→Embeddings→Index

Query pipeline

User question→Auth + guards→Query processing→Hybrid retrieval→Rerank→Context→LLM→Cited answer

Evaluation, observability, security controls and document lifecycle management span both pipelines.

03

Practical learning path

Build in small, testable increments rather than implementing everything at once.

Phase 1 · Define scope

Identify users, data sources, languages, file types, permissions and question types. Create a small gold set of questions and expected evidence.

Phase 2 · Build ingestion

Validate files, parse text/tables, OCR scanned pages, chunk content, attach metadata and index embeddings. Make ingestion idempotent.

Phase 3 · Build retrieval

Implement vector search, lexical search for exact terms, metadata filters, hybrid ranking and reranking. Return traceable sources.

Phase 4 · Ground generation

Use controlled prompts, source citations, insufficient-evidence behavior and response-schema validation.

Phase 5 · Evaluate

Measure retrieval recall/ranking, answer correctness, faithfulness, citation quality, latency and cost.

Phase 6 · Productionize

Add authentication, authorization, retries, timeouts, caching, observability, CI tests, containerization and deployment.

Suggested hands-on exercise: Index 20–30 representative documents, including a scanned PDF, a table-heavy PDF, exact identifiers and a superseded document. Compare vector-only retrieval with hybrid retrieval, then measure reranking and metadata filters.
04

1. Document ingestion challenges

Bad extraction becomes bad retrieval. Fix source quality before tuning prompts.

ChallengeRoot causeRecommended fixValidate
Multi-column PDFsReading order mixes separate columns.Use layout-aware extraction; preserve headings, columns and page metadata.Compare extracted order with representative pages.
Tables in PDFsCells lose their row/column relationship.Extract tables separately; retain title, headers, rows and page. Normalize as Markdown or JSON.Verify values remain associated with correct headers.
Scanned/image PDFsNo embedded text layer exists.Detect text-poor pages and apply OCR or vision-based document processing. Retain confidence and page number.Review low-confidence pages and sample OCR output.
Password-protected filesParser cannot open protected content.Request an authorized accessible copy. Do not bypass permissions; record failure clearly.Failed files are quarantined, not silently skipped.
Corrupted filesParser may return partial or misleading output.Validate early, quarantine and retry only after a corrected file is supplied.Store ingestion status and error reason.
ArchivesNested, unsupported or oversized content.Allowlist file types; enforce size/depth limits; scan and deduplicate using content hashes.Test unsupported types and archive limits.

Chunking: practical guidance

  • Prefer semantic boundaries such as headings, paragraphs and list groups over arbitrary splits.
  • Keep chunk size appropriate to the embedding model and expected question granularity.
  • Use overlap only where context continuity requires it; excessive overlap creates duplicate retrieval.
  • Carry document ID, page, section, version, effective date and access metadata into every chunk.
  • Keep a stable chunk ID so citations and reindexing remain traceable.
05

2. Retrieval and search challenges

Choose retrieval strategy based on the question, not because a vector database is available.

ChallengeRoot causeRecommended fixValidate
Short / ambiguous queryToo little context for semantic search.Rewrite using conversation context; expand acronyms; use multiple query variants selectively.Compare retrieval for original and expanded query.
Exact IDs / codesDense embeddings are weak at exact string matching.Add BM25/lexical search, normalize identifiers and filter by metadata.Known ticket IDs and error codes must be retrievable.
Multi-document questionEvidence is spread across sources.Decompose into sub-questions; retrieve evidence per sub-question; use multi-hop retrieval when needed.Each part of the answer has supporting evidence.
Outdated informationOld chunks or cached results remain active.Store version, effective date and status; supersede old chunks; invalidate caches.Superseded content is not presented as current.
Multilingual searchQuery and source languages differ.Use suitable multilingual embeddings; consider language detection/translation; preserve original text.Evaluate retrieval separately for each supported language.

Query enhancement patterns

Query rewriting: expand an unclear user question into a self-contained search query using relevant conversation context.

Query decomposition: split a complex question into smaller searches whose evidence can be combined.

HyDE: generate a hypothetical answer-like passage to improve retrieval matching. The generated passage is a search aid, not factual evidence.

Multi-hop retrieval: use an intermediate result to formulate a follow-up search when one retrieval step cannot find all relevant evidence.

3. LLM generation challenges

Correct retrieval is necessary, but not sufficient for a reliable answer.

Hallucination

Cause: The model fills evidence gaps using prior knowledge.

Fix: Grounding instructions, source citations, explicit insufficient-evidence behavior and claim-to-source checks.

Context too long

Cause: Too many or redundant chunks exceed the token budget.

Fix: Rerank, deduplicate, compress query-relevant content and reserve tokens for instructions and response.

Inconsistent answers

Cause: Ambiguous prompts, weak evidence or variable generation.

Fix: Stable prompt templates, structured output, controlled parameters and regression datasets.

Weak citations

Cause: Source references are lost during context assembly.

Fix: Carry chunk IDs and source metadata through every stage; validate citation support.

Important: A citation existing is not proof that it supports the claim. Evaluate citation precision and coverage, not just citation presence.
07

4. Production challenges

Measure each stage independently to locate bottlenecks and failure modes.

ChallengeRoot causeRecommended fix
High latencySequential network calls and oversized context.Measure stage latency; use async I/O; parallelize independent retrieval; stream when useful.
API rate limitsProvider quotas or concurrency exceeded.Exponential backoff with jitter, bounded retries, request queues and concurrency limits.
Provider outageSingle external dependency.Use a tested fallback where policy permits; return graceful errors when unavailable.
Cold startsClients/models/indexes initialize on first request.Initialize reusable clients at startup; readiness checks; warm-up; measure cold and steady-state latency.
Stale cacheCache key ignores source or index version.Version-aware cache keys, TTLs and explicit invalidation after source changes.
Poor visibilityNo end-to-end traces.Correlation IDs, structured logs, latency/token metrics, retrieval traces and alerts; redact sensitive data.

Useful operational metrics

  • Ingestion: processed/failed files, extraction quality, OCR confidence, index freshness.
  • Retrieval: recall@k, precision@k, MRR, nDCG, empty-result rate and filter behavior.
  • Generation: faithfulness, correctness, citation coverage, refusal/insufficient-evidence rate.
  • Operations: p50/p95 latency by stage, error rate, token usage, provider spend and cache hit rate.

5. Security and privacy

Security belongs in the ingestion and retrieval architecture, not only in the API gateway.

ChallengeRiskRecommended fix
Prompt injection in documentsRetrieved text tries to override model instructions.Treat retrieved text as untrusted data; delimit it; restrict tools and actions in application code.
Cross-tenant retrievalA user accesses another tenant's content.Authorize before retrieval; apply server-side tenant/access filters; test negative cases.
PII in chunksSensitive data may be embedded, retrieved or logged.Classify data; mask/tokenize where feasible; enforce access and retention; redact traces.
API key exposureCredentials committed to source control.Use environment variables locally and managed secrets in production; rotate exposed keys; least privilege.
Cache leakageOne user's cached response is served to another.Include tenant and permission scope in cache keys; isolate personalized results.
Never rely on the LLM to enforce authorization. Permission checks and data filtering must happen in trusted application code before evidence reaches the model.

Retrieval strategy decision guide

Match the search method to the information need.

Question typeUseful approach
Conceptual / natural languageDense vector retrieval
Exact error code, ticket ID, SKU, policy numberBM25 / lexical search
Mixed semantic and exact termsHybrid retrieval + rank fusion
Question spans several documentsQuery decomposition + multi-hop retrieval
Unclear wordingQuery rewriting; selective HyDE
Versioned or time-sensitive policyMetadata filters for status, effective date and version
Multilingual questionMultilingual embeddings and language-aware evaluation

Hybrid search note: Combine ranked lists using a rank-fusion strategy such as Reciprocal Rank Fusion (RRF). Avoid adding raw scores from unrelated search systems unless calibrated.

Recommended chunk metadata schema

Metadata supports citations, filtering, lifecycle management and access control.

JSON example · adapt to your authorization model
{
  "chunk_id": "doc-123:page-4:chunk-02",
  "document_id": "doc-123",
  "source_name": "support-policy.pdf",
  "page_number": 4,
  "section_title": "Priority response times",
  "chunk_index": 2,
  "document_version": "3",
  "effective_date": "2026-10-01",
  "ingested_at": "2026-11-11T00:00:00Z",
  "language": "en",
  "tenant_id": "tenant-a",
  "access_groups": ["support"],
  "content_hash": "sha256:...",
  "parser": "layout-aware-pdf-parser"
}

Do not expose internal source URIs, tenant identifiers or access metadata to unauthorized users. Apply access filters server-side.

Evaluation: measure the whole system

Do not judge RAG only by whether the answer sounds fluent.

LayerMetrics / checksExample evaluation question
IngestionExtraction completeness, OCR quality, metadata accuracyDid the parser preserve the table headers?
RetrievalRecall@k, Precision@k, MRR, nDCGDid the correct source appear near the top?
GenerationCorrectness, faithfulness, completenessIs every claim supported by evidence?
CitationsCitation precision and coverageDoes each citation support the sentence?
Operationsp50/p95 latency, error rate, token costIs the service reliable under load?
SecurityAuthorization pass/fail, leakage testsCan one tenant retrieve another tenant's data?
Use human review for a representative sample. Automated metrics are useful signals, not proof of correctness. Keep a fixed evaluation dataset to compare changes against a baseline.

Glossary

Short definitions of commonly used RAG engineering terms.

BM25

Lexical ranking method based on query-term matching.

Dense retrieval

Search using vector representations of text.

Embedding

Numerical representation of text used to compare semantic similarity.

HyDE

Hypothetical Document Embeddings; a generated passage helps retrieval but is not evidence.

Hybrid retrieval

Combination of lexical and semantic search.

Multi-hop retrieval

Additional searches based on intermediate evidence.

OCR

Optical Character Recognition converts text in images into machine-readable text.

Reranking

Reordering candidates using a more precise relevance model.

RRF

Reciprocal Rank Fusion combines ranked lists without comparing raw scores.

Faithfulness

Whether an answer is supported by supplied evidence.

Chunk

A segment of a source document indexed and retrieved as a unit.

Grounded answer

An answer whose claims are traceable to retrieved source evidence.
